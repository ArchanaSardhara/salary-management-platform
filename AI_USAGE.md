**Date:** 2026-11-23

### What was asked

> "Configure NestJS, Prisma, PostgreSQL, environment validation, global
> exception handling and logging."

This followed on from earlier discovery/requirements/architecture work in
the same session (`docs/product-discovery.md`, `docs/requirements.md`,
`docs/feature-plan.md`, `docs/backend-architecture.md`). No business/domain
models were in scope here — this task is pure application infrastructure,
matching `docs/backend-architecture.md` §2's `PrismaModule` and §5's
cross-cutting concerns (auth/validation/transactions/error
handling/logging), minus the not-yet-built feature modules.

### What AI generated

- **Environment validation** (`src/config/env.schema.ts`,
  `src/config/env.validation.ts`): a Zod schema for `DATABASE_URL`, `PORT`
  and `NODE_ENV`, wired into `ConfigModule.forRoot({ validate })` so the
  process fails fast at startup with a readable error if a variable is
  missing or malformed, instead of failing later with a confusing runtime
  error.
- **Prisma / PostgreSQL** (`src/modules/prisma/prisma.service.ts`,
  `src/modules/prisma/prisma.module.ts`): `PrismaService` wraps the
  generated Prisma client using the `@prisma/adapter-pg` driver adapter,
  connects in `onModuleInit` and disconnects in `onModuleDestroy`.
  `PrismaModule` is `@Global()` so every future feature module can inject
  `PrismaService` without importing the module individually — this matches
  the "PrismaModule is the only module that touches Postgres directly"
  design already written in `docs/backend-architecture.md`.
- **Global exception handling**
  (`src/common/filters/all-exceptions.filter.ts`): a single `@Catch()`
  filter so every error response has the same shape (`statusCode`, `error`,
  `message`, `path`, `timestamp`). `HttpException`s keep their own status
  and message; anything else becomes a generic 500 with no internal detail
  leaked to the client. 5xx errors are logged with their stack; the request
  body is never logged, since it may carry salary data (CLAUDE.md security
  rules).
- **Logging**
  (`src/common/interceptors/logging.interceptor.ts`, plus the bootstrap
  logger in `src/main.ts`): one log line per request (method, path, status,
  duration). Also never logs request/response bodies.
- **Wiring**: `src/app.module.ts` now imports `ConfigModule`,
  `PrismaModule` and `HealthModule`; `src/main.ts` registers the global
  filter/interceptor and reads the validated `PORT` from `ConfigService`
  instead of raw `process.env`.
- **Docs**: `backend/README.md` gained an "Environment variables" section;
  `backend/.env.example` added (tracked; the real `.env` stays gitignored).

### Technical decisions

- **Zod over `class-validator` for environment validation.** `backend/AGENTS.md`
  confirms Nest's `StandardSchemaValidationPipe` already works with Zod, so
  this keeps one validation approach available for both env vars now and
  request DTOs later, without adding `class-validator` + `class-transformer`
  and their `reflect-metadata` decorator wiring just for a handful of env
  vars. (Developer decision, confirmed reasonable by the assistant — not
  specified by the user.)
- **No global `ValidationPipe` added yet.** The task asked for environment
  validation specifically, not request-body validation, and there are no
  endpoints with a request body yet to validate. Left for when the first
  feature module with a write endpoint is built.
- **`PrismaModule` is `@Global()`.** Matches the architecture doc's intent
  (every feature module depends on it) and avoids re-importing it in every
  future module.
- **Audit/salary data never logged.** Both the exception filter and the
  logging interceptor deliberately log only method/path/status/duration —
  never the request or response body — per CLAUDE.md's security guidelines
  ("Never log passwords, authentication tokens, or sensitive salary data").
